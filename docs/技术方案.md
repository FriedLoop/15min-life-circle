## 一、系统架构

```
┌──────────────┐        ┌───────────────────────────────┐
│  前端         │  HTTP  │  后端（FastAPI）               │
│  原生 JS      │ ─────► │  routers → services → client  │
│  百度 JS API  │        │                               │
│  SVG 自绘图表 │ ◄───── │  进程内缓存（TTL + LRU）       │
└──────────────┘        └───────────────┬───────────────┘
                                        │ HTTPS
                                        ▼
                        ┌───────────────────────────────┐
                        │  百度地图开放平台              │
                        │  地点检索 / 批量算路 / 地理编码 │
                        └───────────────────────────────┘
```

**设计取舍**：

- 前端用**原生 JS 无构建链**，评审 `docker compose up` 后直接可用，无需 npm install
- 后端**同时托管前端静态文件**，单端口（8000）部署，降低评审启动成本
- 缓存用**进程内内存**而非 Redis：单实例部署即可满足需求，
  引入 Redis 会增加评审环境负担，与"一键跑通"目标冲突

## 二、地图 API 调用策略

### 2.1 使用的服务

| 服务 | 接口 | 用途 |
|---|---|---|
| 地理编码 | `/geocoding/v3` | 地名 → BD09 坐标 |
| 逆地理编码 | `/reverse_geocoding/v3` | 坐标 → 结构化地址（报告标注） |
| 坐标转换 | `/geoconv/v1` | WGS84 / GCJ02 → BD09（本项目基准坐标系） |
| 地点检索 | `/place/v2/search` | 获取各类民生设施 POI |
| 批量算路（步行） | `/routematrix/v2/walking` | 计算真实路网步行耗时 |

### 2.1.1 坐标转换：为什么必须有，以及为什么要有本地兜底

本项目内部统一用 **BD09**（与百度地图 JS API 点击取点一致），但输入坐标可能来自别处：

| 来源 | 坐标系 | 与 BD09 的偏差 |
|---|---|---|
| GPS 设备、GeoJSON、OpenStreetMap | WGS84 | 数百米 |
| 高德 / 腾讯地图、国内合规化的"火星坐标" | GCJ02 | 数百米（≤ 600 m） |

若把 WGS84 / GCJ02 当成 BD09 直接分析，等时圈与盲区结论会**整体平移**，
所以所有分析接口都接受 `coord_type`（`bd09` / `gcj02` / `wgs84`），
入口处先统一转换为 BD09（`services/coordconv.py` 的 `to_bd09_point`）。

转换有两条路径，互为兜底：

| 路径 | 实现 | 精度 |
|---|---|---|
| 官方接口 | `/geoconv/v1`（批量上限 100，本项目按 50 分批） | 与百度地图渲染完全一致 |
| 本地算法 | `utils/coordinate.py`（GCJ02 加密算法 + BD09 解析偏移） | 实测与官方差 2~25 m（东莞境内） |

本地算法的必要性：geoconv 属于独立服务，AK 未开通或被限流时**不能因此让整条分析链路失败**。
差异即便取最坏 25 m，也远小于 150 m 网格间隔与 50 m 缓存量化粒度，
不改变任何结论——符合本项目"宁可降级不可崩"的一贯取舍。
若结果数量与请求数量不一致，同样降级为本地算法，保证坐标与统计口径一一对应。

`utils/coordinate.py` 与百度 geoconv 的差异在 **23.0°N 附近明显放大**：
GCJ02 偏移函数在该纬度带变化陡峭，实现上的微小差别会被放大。三系转换的往返一致性
由 `tests/test_coordinate.py` 守护（三种坐标系往返误差 ≤ 1e-6 度，约 0.11 m）。

### 2.2 配额约束（个人开发者）

| 服务 | 日配额 | 并发 | 本项目单次分析用量 |
|---|---|---|---|
| 批量算路 | 5000 条 | 3 | 网格点数（默认 150m 间隔 = 197）+ 灰色地带精算次数 × 候选数（≤3），实测约 600 条 |
| **地点检索** | **100 次** | 3 | 10 次（逐类检索，每类最多 2 页）← **最紧张** |
| 地理编码 | 5000 次 | 3 | 1 次 |
| 逆地理编码 | 300 次 | 3 | 1 次 |

### 2.3 调用策略

**统一客户端封装**（`services/baidu_client.py`）：

- AK 注入与缺失校验
- `asyncio.Semaphore` 限流，并发上限锁死为 **3**（超了会被百度限流）
- 指数退避重试，**只对网络类错误重试**——配额超限、参数错误等业务错误重试无意义
- 错误归一化，统一抛 `BaiduApiError`，由全局异常处理器转成 HTTP 400/503

**批量算路的分批策略**：

网格点通常上百个，单次请求的终点数取 **50**（百度文档未公开硬上限，
参考 HarmonyOS 侧文档"起点数 × 终点数 < 100"）。197 个网格点仅需 4 个请求。

**地点检索的省配额策略**：

1. 结果按 (量化坐标, 半径, 类别) 缓存
2. 支持按需指定类别，调试时只查关键三类
3. 翻页上限 2 页（40 条），稀疏类别不足一页时自动提前停止

### 2.4 静默失败的防御

并发请求中个别类别可能失败（限流、网络抖动）。
**失败绝不能被当成"该区域没有此类设施"**——否则会得出完全错误的盲区结论。

因此 `search_all_categories` 显式返回 `(结果, 失败类别列表)`：

```python
pois_by_category, failed_categories = await search_all_categories(...)
```

失败类别会：

- 写入响应的 `failed_categories` 字段
- 前端以红色文字显著提示"这部分覆盖率不可信"
- **阻止结果进入缓存**，避免错误结论被反复复用

## 三、等时圈生成算法设计

### 3.1 算法：网格采样 + 真实路网算路

```
1. 以中心点生成半径 1200 m、间隔 150 m 的网格（约 197 点，圆形裁剪）
2. 分批调用步行批量算路，取得每个网格点的真实步行耗时 duration
3. 筛选 duration ≤ 900 秒（15 分钟）的点 → 可达集合
4. 输出：逐点耗时与可达标记（供前端逐格绘制，并被盲区分析复用）

注：等时圈边界不在后端生成——轮廓由前端按网格单元逐格描边还原，
以保留凹陷与缺口。原 `polygon`（凸包）字段已移除。
```

### 3.2 为什么用网格法，而不是射线法

| 方法 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 射线法 | 沿 N 个方向各算一条路径，终点连成多边形 | 调用量小（约 36 次） | 只有边界稀疏点，**无法表达内部耗时差异，画不出热力图** |
| **网格法** | 铺满网格，逐点算路 | 内部有完整耗时分布，既能画热力图，又能直接复用于盲区分析 | 调用量较大（约 197 条） |

赛题评分标准明确要求「**热力图**」展示，网格法是唯一能同时满足
"热力图"与"批量距离矩阵并发请求"两项评分点的选择。

### 3.3 两种热力图：设施可达性（默认）与步行耗时

同一份网格数据支持两种着色，前端可一键切换。二者不是替代关系，而是互补：

| 图层 | 着色依据 | 表达什么 | 用途 |
|---|---|---|---|
| **设施可达性**（默认） | 该点的综合可达性得分 | 周边设施的便利程度 | 直接对应"体检"结论，**红区即盲区** |
| **步行耗时** | 该点的真实路网耗时 | 这段路走起来多费劲 | 直观证明等时圈不是圆：同一个直线距离上，路网稀疏方向的耗时明显更长 |

「步行耗时」图层的着色范围是**全部采样点（含圈外）**，因此它的图形外轮廓就是采样范围，
圈内外的分界由等时圈边界线给出，两者叠加即可读出"走到哪里开始超时"。
若只给圈内着色，颜色梯度会被边界截断，反而看不出路网不规则。

之所以把「设施可达性」设为默认：它是"体检"的直接结论，而耗时图只是它的成因说明。
早期版本仅耗时着色，覆盖率 100% 的区域也会因"走得远"而发红，
与"覆盖率高"这一事实自相矛盾（详见下节）。

**可达性得分**采用「可及即满分」口径，按类别权重加权平均：

```
score = Σ(wᵢ × coveredᵢ) / Σ(wᵢ),   coveredᵢ ∈ {0, 1}
```

- `coveredᵢ`：该点到第 i 类设施的路网距离是否 ≤ 判定阈值（1000 m），
  是记 1、否记 0；若区域内根本没有该类设施，该项为 0
- `wᵢ`：类别权重，赛题点名的三类为 1.5，其余为 1.0
- 得分区间 0~1，1 表示最便利

**为何不用距离线性衰减**（`1 − d / threshold`）：判定阈值本身就是 1000 m，
一个距离 900 m 的设施按定义已经可及；若按线性衰减计分它只得 0.1 分，
于是覆盖率 100% 的区域也会被算成接近 0 而整片发红，与"覆盖率高"这一事实自相矛盾
（莞城实测即因此整片发红）。故采用「可及即满分」口径，实现在
`services/blindspot.py` 的 `_accessibility_score()`。

由于只在等时圈范围内着色，**图形外轮廓就是真实等时圈边界**，
颜色则表达可达性——一张图同时满足「等时圈热力图」与「盲区识别」两项评分要求。

### 3.4 为什么不用凸包做轮廓

凸包是"包含所有点的最小凸多边形"，会**把可达范围的凹陷与缺口全部抹平**，
画出来又变成接近圆的形状——这与直接画圆没有本质区别，
恰恰丢掉了"真实路网 ≠ 直线距离"这一核心结论。

因此前端**按网格单元逐个绘制半透明正方形色块**：相邻格子无缝拼接成连续的面，
完整保留凹陷与缺口（那是河流、铁路阻断的证据）。
再遍历每个可达格子，凡是某个方向没有相邻可达格子就描出那条边，
拼成完整外轮廓，边界因此比纯色块锐利（见 `js/layers.js` 的 `drawBoundary`）。

后端**不再计算凸包**：原 `polygon` 字段因前端始终未使用，已被移除。

### 3.5 设施点位采用形状 + 颜色双重编码

仅用颜色区分类别对色觉障碍人群不友好。因此十个类别各赋予一种形状
（圆形 / 十字 / 三角 / 菱形 / 方形 / 五角星 / 六边形 / 竖矩形 / 五边形 / 倒三角），
与颜色共同构成双重编码——即使完全无法辨色，也能靠轮廓区分设施类型。

### 3.6 关键参数的实测依据

| 参数 | 取值 | 依据 |
|---|---|---|
| 网格间隔 | 150 m | 200 m 与 150 m 算出的可达面积仅差 1.4%（1.44 vs 1.42 km²），统计口径已收敛；150 m 用于提升热力图细腻度 |
| 网格半径 | 1200 m | 实测 15 分钟可走 1056 m 路网距离，绕行系数 1.33~1.58 对应直线半径 670~790 m；1200 m 覆盖最坏情况并留余量，比初设 1500 m 省约 36% 无效调用 |
| 时间阈值 | 900 秒 | 15 分钟 |

## 四、POI 检索口径与数据清洗策略

### 4.0 为什么只用一个数据源，而不是「多源」

本节原名「多源 POI 数据清洗策略」，但实现是单源（百度）+ 逐类检索。
把标题改成「检索口径与数据清洗」，是因为**单源是刻意的工程决策**，理由有四条：

**1. 可复现性优先于数据源数量。**
评审 clone 仓库后只需要一个百度 AK 就能跑出报告里的全部数字。
引入第二家商业地图服务意味着报告数字依赖两份 AK——任何人（包括评审）都无法复现，
而「一键跑通、数字可复现」是本项目的核心交付承诺。

**2. 跨源去重没有 ground truth，误差无法量化。**
同一家药店在百度叫「东莞国药（虎门长德药店）」、在另一家叫「长德药房」，
坐标还差几十米。去重规则（空间阈值 + 名称相似度）本身会**新增一个误差来源**，
且这个误差**不可验证**——百度说 1 家、另一家说 2 家，谁对？
相比之下，「少收录一个小微设施」是可接受且可量化的已知偏差。

**3. 决定结论质量的是检索口径，不是数据源数量。**
实测已经证明这一点：并集检索下莞城 1000 m 内返回的 20 条里 18 条是药店，
菜市场与小学被直接挤掉（§4.1）。这个坑是**口径问题**，
换成第二家数据源照样存在；解决它靠的是逐类检索 + 半径裁剪 + 归一化（§4.2~4.3）。

**4. 换源的前置条件（坐标系归一）已经具备。**
`coord_type` 参数 + `utils/coordinate.py` 已支持 WGS84 / GCJ02 / BD09 互转，
任何数据源（高德 QCJ02、OSM WGS84、政务数据 CGCS2000）的坐标都能直接接入，
未来只需补一个适配器。这条写进「未来工作」，成本清晰。

**另外实测排除了最常见的替代源。** OSM 是唯一无需申请即可用的开放数据源，
但 2026-10-16 实测：松山湖 2 km 内名称含「药 / 小学 / 菜市场 / 农贸」的要素为 **0 条**，
广州天河 1 km 内任意 `amenity` 为 **0 条**，松山湖 20 km 内药店仅 **1 条**——
不是网络问题（瑞士镜像 1.6 s 即通），而是**中国境内本就几乎没有数据**。

**但「单源」不等于「不校验」。** 数据本身可不可信，用**政务公开的权威名录**来交叉验证，
方法与实测结果见 §4.5——那才是真正能回答「POI 检索可不可信」的东西。

### 4.1 问题：并集检索会被单一类别淹没

百度地点检索支持 `$` 分隔的多关键字并集检索（最多 10 个），
理论上一次请求即可拿到全部类别。但实测发现严重问题：

**在莞城老城区，1000 m 内各类设施共 104 个，返回的前 20 条里 18 条都是药店**，
菜市场、小学等类别被完全挤掉。

原因：接口只返回前 20 条，且按综合相关性排序而非按类别均衡。
据此统计会得出「该区域没有小学」这类严重失真的结论。

### 4.2 解决方案：按类别分别检索

改为每个类别单独发起请求：

```
菜市场 → 1 次请求 → 该类的全部结果
药店   → 1 次请求 → 该类的全部结果
...
```

代价：单次分析从 1 次检索变为 10 次。通过结果缓存与"按需指定类别"缓解。

### 4.3 归一化与清洗

| 步骤 | 处理 |
|---|---|
| 类别归一化 | 按 `FACILITY_CATEGORIES` 关键词表把 POI 归入 10 类民生设施 |
| 匹配优先级 | 顺序敏感，「小学」排在「药店」之前，避免"XX小学门口药店"被误判 |
| 半径裁剪 | 剔除超出检索半径的结果，保证统计口径一致 |
| 距离计算 | 用 Haversine 计算到中心点的球面直线距离 |
| 排序 | 按距离升序，便于后续取最近设施 |
| 去重 | 逐类检索天然避免跨类别重复计数 |

### 4.4 十类民生设施

菜市场、药店、小学、幼儿园、医疗、购物、公园、银行、养老、餐饮

其中**菜市场、药店、小学**为赛题明确点名的盲区判定类别，权重更高。

### 4.5 权威名录交叉校验：百度检索可不可信

覆盖率、盲区率、健康度分数全部建立在百度 POI 检索之上。
百度是**商业收录**，一旦漏掉真实存在的设施，覆盖率会虚低、盲区率会虚高，
而报告本身看不出任何异常。所以引入一份**不依赖百度**的基准来交叉验证。

**数据来源（政务公开，非商业地图服务）**，由 `scripts/collect_authority_data.py`
采集后冻结为 `scripts/authority_benchmark/*.csv`（含发布单位与统计截止日期清单）：

| 类别 | 发布单位 / 文件 | 镇街内条数 | 含地址 |
|---|---|---|---|
| 药店 | 东莞市医疗保障局·市内定点药店查询 | 松山湖 33 / 莞城 64 / 虎门 135 | ✅ |
| 幼儿园 | 东莞市教育局·公办（集体办）幼儿园一览表 | 5 / 6 / 20 | ✅ |
| 小学 | 东莞市教育局·义务教育标准化学校名单 | 8 / 10 / 37 | ❌ 仅镇街 |
| 养老 | 东莞市民政局·在运营养老机构信息表 | 0 / 1 / 2 | ✅ |
| 菜市场 | 东莞市市场监督管理局·五星农贸市场名单 | 0 / 0 / 1 | ✅ |

**方法**（`scripts/authority_benchmark.py`，三步只围绕「召回」这一个方向）：

```
1. 用百度地理编码把名录里的设施地址解析成 BD09（322 条，可定位 317 条）
2. 只保留落在检索半径 2000 m 内的记录 —— 它们「本应」被地点检索发现
3. 调百度地点检索取该类目结果，与名录配对，统计命中 / 未覆盖
```

**配对判据必须用名称，不能用距离**——这是本次校验踩到并修掉的第一个坑：
最初只用「距离 ≤ 100 / 300 m」配对，得到的未覆盖距离密集落在
372~536 m（莞城药店）、1024~1062 m（莞城小学）。这不是百度没收录，
而是**地址地理编码只精确到路口**，与 POI 的建筑物入口坐标天然差几百米。
改用「归一化名称最长公共子串 ≥ 5 字且占比 ≥ 60%」为主判据后，
未覆盖数从 33 条降到 22 条，校园类直接升到 100%。

**实测结果（2026-10-16，三个样例点位，检索半径 2000 m）**：

| 类别 | 半径内权威数 | 命中 | 召回率 | 未覆盖 | 其中「百度库里有」 | 其中「名称直查也没有」 |
|---|---|---|---|---|---|---|
| 幼儿园 | 7 | 7 | **100%** | 0 | — | — |
| 小学 | 8 | 3 | 37.5% | 5 | **4** | 1 |
| 药店 | 47 | 19 | 40.4% | 28 | **7** | 21 |
| 合计 | 62 | 29 | 46.8% | 33 | **11** | 22 |

「百度库里有」的判定方式：对未覆盖的记录**按名称直查**百度 POI 库
（`--diagnose` 模式，每条多消耗 1 次检索配额）。
若名称直查命中，说明百度**库里有这家店**，只是没进入我们的类目检索结果。

**三条结论**：

**① 校园类的覆盖率统计是可信的。** 幼儿园 7/7 全部命中；
小学未覆盖的 5 条里有 4 条被证明「百度库里有」。
即校园类设施的统计没有系统性缺漏。

**② 有一个确证的、属于本项目自己的口径缺陷：密集区域会被 40 条上限截断。**
地点检索每类最多翻 2 页 × 20 条 = **40 条**，且实测返回的 40 条
**按相关性而非距离**散落在半径内——莞城药店返回的 40 条距离跨 398~1811 m（中位 1211 m），
虎门跨 191~1808 m（中位 777 m）。也就是说：**半径内还有大量同类设施根本没被返回**，
而其中有比已返回者更近的。莞城/虎门的药店与幼儿园检索**全部触顶**，
权威名录里 17 家医保定点只覆盖到 6 家、28 家只覆盖到 12 家。

这直接影响覆盖率与盲区率的方向是**低估可达性**（少算了设施 → 覆盖率虚低、盲区率虚高）。
它与 §5.4 的绕行系数问题是**同一类方向**的偏差，都偏保守。

**已评估、暂不修正（2026-10-16 决策）**：提高翻页数会让地点检索消耗
从约 10 次/分析升到约 30 次/分析，而日配额仅 100 次，可用分析次数将从约 10 次降到 3 次。
这是**配额换精度的取舍，不是可以顺手改掉的疏漏**——决策与实测证据记录在
`constants.py` 的 `POI_MAX_PAGES` 处及本节的测试报告对应条目中，供后续维护者复核。

**③ 剩余 22 条「名称直查也没有」不能判为百度未收录。**
政务名录登记的是**工商注册名**（如「东莞市虎门宁馨药店」），
百度 POI 展示的是**门店名**（如「海王星辰健康药房（虎门宁馨店）」），
两者差异可以很大；叠加地址地理编码的路口级精度，
这 22 条既无法证明「百度有」、也无法证明「百度没有」，属**无法判定**。
要彻底定论需要人工实地核对，成本与收益不成比例，故如实标注而不强行归因。

**不成立的结论（必须写清楚，避免被误读）**：
- **不能**把「百度有、名录无」判为误检：名录本身就不全
  （药店仅医保定点、幼儿园仅公办、农贸市场仅星级评定），
  脚本对此只做展示不做判定；
- **不能**由本校验反推真实世界的设施总数：权威名录是**子集**，
  它只能作为「召回」检验的分子，不能当分母。

## 五、服务盲区识别算法

### 5.1 判定语义

对**15 分钟等时圈内的每个可达点**，判断其周边 1000 m 内能否找到指定类别的设施。
找不到 → 该点在该类别上属于盲区；**判定类别中缺失任一** → 该点记为服务盲区。

只判定可达点（而非全部网格点），因为走不到的地方本就不属于生活圈。

**判定类别 ≠ 统计类别**：检索与覆盖率统计默认覆盖全部 10 类，
但「是否盲区」默认只针对赛题点名的三类（菜市场 / 药店 / 小学，
见 `constants.BLINDSPOT_CATEGORIES`）。若改用全部 10 类判定，
养老这类普遍稀缺的设施会让几乎所有点都命中缺失，盲区率被推向 100%，失去区分度。
接口可通过 `blindspot_categories` 参数覆盖默认判定类别。

**判定类别的派生规则（2026-10-16 修正）**：

```
显式传入 blindspot_categories  → 按传入的来，并自动补进检索范围
未传入                        → 取「赛题三类 ∩ 检索类别」；交集为空则不判定
```

修正前这里写的是「无条件把赛题三类补进检索类别」。后果是：
用户在界面上取消勾选菜市场 / 药店 / 小学后，报告里**仍然冒出完整的这三类**——
覆盖率、逐类盲区率、健康度全被悄悄扩回全量，用户的筛选形同虚设（已复现并修复）。

取交集后留下的问题是「未判定」与「没有盲区」在数字上都是 0，
两者绝不能混为一谈。因此约定：`judge_categories` **为空列表即表示本次未做盲区判定**，
`blind_points` 恒为 0 但不得被解读为「没有盲区」。
前端据此做了三处配套：类别勾选区出现橙色警示、概览把「盲区占比」显示为「未判定」、
报告顶部与地图控件明确写出「本次不做盲区判定」并隐藏盲区标注类别下拉。

> **前置依赖的口径偏差**：本节的判定全部建立在「POI 检索结果」之上。
> §4.5 的权威名录校验证明：密集区域（莞城、虎门老城区）的类目检索会触到
> **每类 40 条的翻页上限**，且百度按相关性而非距离排序，因此半径内仍有同类设施未被返回。
> 偏差方向是**少算设施 → 覆盖率虚低、盲区率虚高**，与 §5.4 的绕行系数问题同向，都偏保守。
> 未修正的原因与代价见 §4.5 结论②：修正需提高翻页数，地点检索日配额仅 100 次，
> 10 类 × 3 页 = 30 次/分析会让可用分析次数从 10 次降到 3 次——这是明确的取舍，不做静默改动。

### 5.2 核心优化：直线初筛

对每个点、每个类别，记 `d` = 到该类最近设施的**直线距离**：

| 条件 | 结论 | 是否需要调 API |
|---|---|---|
| 该类在检索范围内无设施 | 必然盲区 | ❌ 否 |
| `d > 1000 m` | 必然盲区（路网距离 ≥ 直线距离） | ❌ 否 |
| `d < 625 m`（1000 ÷ 绕行系数 1.6） | 必然非盲区（路网 ≤ d × 1.6 < 1000） | ❌ 否 |
| `625 m ≤ d ≤ 1000 m`（灰色地带） | 需真实路网距离才能定论 | ✅ **是** |

前三类结论无需调用 API 即可得出。

> **前提与已知偏差**：`d < 625 m → 必然非盲区` 依赖「路网距离 ≤ 1.6 × 直线距离」。
> 该上界在**路网被水域 / 围墙切断**处会被突破：实测松山湖校区存在直线 424~618 m、
> 真实耗时 1023~1480 s 的点（等效绕行系数 **2.8**）。这类点会被初筛判为"非盲区"，
> 即**漏报**。取舍是刻意的（见 §5.4），完整实测见 §6.4。

**实测效果**：

| 点位 | 判定总次数 | 实际调用算路 | 节省 |
|---|---|---|---|
| 松山湖 | 63 × 10 = 630 | 135（21.4%） | 78.6% |
| 莞城 | 55 × 10 = 550 | 103（18.7%） | 81.3% |

约**八成判定由初筛直接得出**。

### 5.3 灰色地带精算

对落入灰色地带的点，取直线距离最近的 **3 个候选设施**（而非 1 个，
因为"直线最近"未必是"路网最近"），调用批量算路取真实路网距离，
再按 `min(路网距离) ≤ 1000 m` 判定。

### 5.4 绕行系数的取值

`DETOUR_FACTOR` 取 **1.6**，依据是**常规路网**下实测的绕行系数 1.33~1.58。

取值偏小的后果：把真实盲区误判为"可达"（**漏报**）。
漏报比多算几个点严重得多，因此宁可保守。

但 1.6 只覆盖"常规路网"。2026-10-15 的对照实验发现：
松山湖校区被水域与围墙切断，存在直线 424~618 m、真实步行耗时 1023~1480 s 的点，
等效绕行系数达 **2.8**。要让初筛对这类点也成立，系数得提到 2.9，
代价是灰色地带急剧变宽、节省从 80% 掉到约 20%，得不偿失。

因此这里的取舍是明确的：**接受少量漏报，换取八成算路节省**。
若要彻底消除，只能把初筛结论也纳入抽样复核，或直接改用单级精细网格
（`/api/isochrone` 与 `/api/report` 的默认策略就是后者，见 §6.4）。

### 5.5 POI 检索半径必须大于等时圈半径

盲区判定的是"每个点周边 1000 m"，而最远可达点距中心可达约 764 m，
它 1000 m 内的设施可能位于距中心 **1764 m** 处。

若 POI 只按 1000 m 半径检索，边缘点会因"远处明明有设施却没检索到"
而被误判为盲区。因此检索半径设为 **2000 m**。

## 六、无需底层路网的连通性推导

### 6.1 问题：只有"点到点"的耗时，没有路网拓扑

百度批量算路返回的是「起点 → 终点」的耗时，
**拿不到路网本身**——既没有节点表也没有邻接表。
因此区域无法像图算法那样做 flood fill，只能靠**采样**去逼近：

- 采样点太稀 → 边界粗糙、内部没有梯度，画不出热力图
- 采样点太密 → 算路配额按平方增长

### 6.2 做法：规则栅格上的真实采样 + 邻接重建

把网格采样理解为「在规则栅格上做真实采样」，连通性则由**邻接关系**重建，分三步：

```
1. 采样：以中心点为中心铺满半径 R、间隔 S 的规则栅格，逐点真实算路 → duration
2. 判定：duration ≤ 阈值 → 该格可达（这一步完全来自真实路网，不是插值）
3. 重建：把相邻的可达格子拼成面；某条边没有相邻可达格子就描出该边 → 外轮廓
```

关键点在于：**判断"这一格属不属于生活圈"只需要该格自己的耗时**，
不需要知道它与邻城之间的路怎么走；而"这片区域连不连得起来、哪里被河道切断"
则交给第 3 步的栅格邻接来还原。两端各用最合适的表示，
既避开了"必须拿到路网拓扑"的硬约束，又保留了凹陷与缺口
（凸包方案会把这些抹平，见 §3.4）。

由此还带来一个工程上的好处：**采样精度是可调的旋钮**——
S 调大省配额、调小更精细，而"可达性来自真实算路"这一性质始终不变。

### 6.3 扇形采样 / 射线法为什么被否

射线法（扇形采样）沿 N 个方向各取若干距离，调用量确实更小，
但代价是**采样点落在射线上、不构成规则栅格**：

| 问题 | 说明 |
|---|---|
| 内部成空洞 | 相邻射线之间是数十米到数百米的空档，中部尤其稀疏，热力图会出现大面积无数据区 |
| 位置偏差 | 空档处的可达性只能靠插值猜，猜错的格子不一定落在正确位置——面积可能"碰巧对上"，形状却对不上 |
| 无法逐格复用 | 盲区分析需要"每个可达点周边缺什么设施"，射线上的点无法代表整片区域 |

### 6.4 三策略实测对照（含 IDW 插值）

为把上面这些判断变成数字，`backend/scripts/compare_grid_strategies.py`
对三种策略做了对照实验：先对**全部**网格点做一次真实算路得到基准真值，
再让各策略在真值上评估，保证"面积误差"量的是同一把尺子。

对照策略中新增的 **IDW（反距离加权）插值**用于补全未采样点的耗时：

```
v = Σ(wᵢ·vᵢ) / Σwᵢ,   wᵢ = 1 / dᵢ^power
```

取距离最近的 `IDW_NEIGHBORS`（默认 8）个已采样点，`IDW_POWER`（默认 2）为衰减指数。
实现见 `utils/geo.py` 的 `idw_interpolate`。

**实测（松山湖校区，2026-10-15，150 m 网格、15 分钟）**：

| 策略 | 算路调用 | 省配额 | 可达面积 | 面积误差 | IoU |
|---|---|---|---|---|---|
| 单级精细网格（默认，基准） | 197 | — | 1.417 km² | 0%（基准） | 1.00 |
| 分级网格 + IDW | 125 | **36.5%** | 1.530 km² | **7.94%** | 0.93 |
| 扇形采样 + IDW（20 向 × 6 环） | 120 | 39.1% | 1.417 km² | 0% | 0.88 |

读法：

- **分级网格**省 36.5% 算路，但可达面积高估 **7.94%**：被几何剪掉的点里，
  有 5 个实际被水域 / 围墙切断（即 §5.4 说的绕行系数 2.8 那批点）。
  所以它被定位为**有损近似、默认关闭**，界面上会显式标注误差。
- **扇形采样**面积误差看似为 0，但那只是"多算的与少算的相互抵消"：
  IoU 仅 0.88，说明约 12% 的格子位置判断错了。这正是 §6.3 说的
  "面积可能碰巧对上、形状对不上"。
- 结论：**默认用单级精细网格**。省配额约 36% 不值得用 8% 的面积误差去换，
  除非配额确实吃紧；那时 `coarse_grid=true` 是可用的、且误差已知的选项。

IDW 只用于给"已由几何定论"的点补一个耗时值供热力图着色，
**不参与可达性判定**：实测必然可达区（52 个点）耗时插值的中位误差为 114 秒
（阈值 900 秒），必然不可达区（20 个点）中位 126 秒——后者本就只要求"判定为不可达"。
需要如实说明的是，可达区插值的**最大**误差为 635 秒，正是 §5.4 那批被水域切断的点：
插值方法（无论 IDW 还是别的）都无法从周围样本"猜"出一条被地形打断的路，
这类点只能靠真实算路发现。等时圈边界始终由真实算路决定，不受此影响。

## 七、降级容错设计

| 场景 | 降级策略 |
|---|---|
| 批量算路不可用（配额耗尽 / AK 失效） | 退化为「直线距离 × 绕行系数 ÷ 步行速度」估算，响应标记 `degraded: true` |
| 单个网格点算路失败 | 该点 `duration` 记为 `null`，视为不可达 |
| 个别类别检索失败 | 记入 `failed_categories`，前端显著提示，**不进入缓存** |
| 灰色地带精算失败 | 退回直线判定，标记不精确 |
| 逆地理编码失败 | 地址留空，不影响报告主体 |

**关键细节**：百度对算路失败的点返回 `duration = 0`。
若直接采信，这些点会被当成"0 秒到达"，在热力图上变成最核心区域。
必须识别为失败：`duration <= 0 → None`。

## 八、配额与性能优化汇总

| 手段 | 效果 |
|---|---|
| 直线初筛 | 砍掉约 80% 的盲区算路调用 |
| 网格半径实测修正（1500→1200 m） | 省约 36% 无效算路 |
| 批量算路分批（每批 50 终点） | 请求数从 10 降到 4 |
| 三级结果缓存（等时圈 / POI / 分析报告） | 重复查询零消耗，坐标量化到 50 m |
| 按需指定类别 | 调试时可从 10 类降到 3 类 |
| 并发限流 3 | 避免触发限流导致整批失败 |
| 分级网格 + IDW（`coarse_grid=true`） | 等时圈算路量再降 36.5%（125/197），代价是面积误差 7.94%，**默认关闭** |

优化效果不是估算值，而是可核对的实测值：响应里的 `isochrone.routed_points`
（本次真实发起的算路终点数）、`isochrone.interpolated_points`（插值补全的点数）
与 `blindspot.precise_calls`（灰色地带精算次数）都会回传给前端展示。

单次完整分析：约 **网格点数（默认 197）+ 灰色地带精算次数 × 候选数（≤3）
+ 10 次地点检索**，两个样例点位实测约 600 条算路；
在批量算路日配额（5000 条）下可运行约 8 次（配合缓存实际更多）。

> 注：`/api/isochrone` 与 `/api/report` 的网格间隔均取配置
> `GRID_STEP_M`（默认 150 → 197 点），请求中 `step_m` 留空即可。
