## 一、系统架构

```
┌──────────────┐        ┌───────────────────────────────┐
│  前端         │  HTTP  │  后端（FastAPI）               │
│  原生 JS      │ ─────► │  routers → services → client  │
│  百度 JS API  │        │                               │
│  SVG 自绘图表 │ ◄───── │  进程内缓存（TTL + LRU）       │
└──────────────┘        └───────────────┬───────────────┘
                                        │ HTTPS
                                        ▼
                        ┌───────────────────────────────┐
                        │  百度地图开放平台              │
                        │  地点检索 / 批量算路 / 地理编码 │
                        └───────────────────────────────┘
```

**设计取舍**：

- 前端用**原生 JS 无构建链**，评审 `docker compose up` 后直接可用，无需 npm install
- 后端**同时托管前端静态文件**，单端口（8000）部署，降低评审启动成本
- 缓存用**进程内内存**而非 Redis：单实例部署即可满足需求，
  引入 Redis 会增加评审环境负担，与"一键跑通"目标冲突

## 二、地图 API 调用策略

### 2.1 使用的服务

| 服务 | 接口 | 用途 |
|---|---|---|
| 地理编码 | `/geocoding/v3` | 地名 → BD09 坐标 |
| 逆地理编码 | `/reverse_geocoding/v3` | 坐标 → 结构化地址（报告标注） |
| 地点检索 | `/place/v2/search` | 获取各类民生设施 POI |
| 批量算路（步行） | `/routematrix/v2/walking` | 计算真实路网步行耗时 |

### 2.2 配额约束（个人开发者）

| 服务 | 日配额 | 并发 | 本项目单次分析用量 |
|---|---|---|---|
| 批量算路 | 5000 条 | 3 | 网格点数（默认 150m 间隔 = 197）+ 灰色地带精算次数 × 候选数（≤3），实测约 600 条 |
| **地点检索** | **100 次** | 3 | 10 次（逐类检索，每类最多 2 页）← **最紧张** |
| 地理编码 | 5000 次 | 3 | 1 次 |
| 逆地理编码 | 300 次 | 3 | 1 次 |

### 2.3 调用策略

**统一客户端封装**（`services/baidu_client.py`）：

- AK 注入与缺失校验
- `asyncio.Semaphore` 限流，并发上限锁死为 **3**（超了会被百度限流）
- 指数退避重试，**只对网络类错误重试**——配额超限、参数错误等业务错误重试无意义
- 错误归一化，统一抛 `BaiduApiError`，由全局异常处理器转成 HTTP 400/503

**批量算路的分批策略**：

网格点通常上百个，单次请求的终点数取 **50**（百度文档未公开硬上限，
参考 HarmonyOS 侧文档"起点数 × 终点数 < 100"）。197 个网格点仅需 4 个请求。

**地点检索的省配额策略**：

1. 结果按 (量化坐标, 半径, 类别) 缓存
2. 支持按需指定类别，调试时只查关键三类
3. 翻页上限 2 页（40 条），稀疏类别不足一页时自动提前停止

### 2.4 静默失败的防御

并发请求中个别类别可能失败（限流、网络抖动）。
**失败绝不能被当成"该区域没有此类设施"**——否则会得出完全错误的盲区结论。

因此 `search_all_categories` 显式返回 `(结果, 失败类别列表)`：

```python
pois_by_category, failed_categories = await search_all_categories(...)
```

失败类别会：

- 写入响应的 `failed_categories` 字段
- 前端以红色文字显著提示"这部分覆盖率不可信"
- **阻止结果进入缓存**，避免错误结论被反复复用

## 三、等时圈生成算法设计

### 3.1 算法：网格采样 + 真实路网算路

```
1. 以中心点生成半径 1200 m、间隔 150 m 的网格（约 197 点，圆形裁剪）
2. 分批调用步行批量算路，取得每个网格点的真实步行耗时 duration
3. 筛选 duration ≤ 900 秒（15 分钟）的点 → 可达集合
4. 输出：逐点耗时与可达标记（供前端逐格绘制，并被盲区分析复用）

注：等时圈边界不在后端生成——轮廓由前端按网格单元逐格描边还原，
以保留凹陷与缺口。原 `polygon`（凸包）字段已移除。
```

### 3.2 为什么用网格法，而不是射线法

| 方法 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 射线法 | 沿 N 个方向各算一条路径，终点连成多边形 | 调用量小（约 36 次） | 只有边界稀疏点，**无法表达内部耗时差异，画不出热力图** |
| **网格法** | 铺满网格，逐点算路 | 内部有完整耗时分布，既能画热力图，又能直接复用于盲区分析 | 调用量较大（约 197 条） |

赛题评分标准明确要求「**热力图**」展示，网格法是唯一能同时满足
"热力图"与"批量距离矩阵并发请求"两项评分点的选择。

### 3.3 热力图的语义：设施可达性（而非步行耗时）

热力图的着色依据是每个网格点的**综合设施可达性得分**，不是步行耗时。
两者的区别：

| 着色依据 | 表达什么 | 问题 |
|---|---|---|
| 步行耗时 | 走得远近 | 只是等时圈的另一种画法，不反映"到了之后有没有东西用" |
| **设施可达性** | **周边设施的便利程度** | 直接对应"体检"结论，**红区即盲区** |

**可达性得分**采用「可及即满分」口径，按类别权重加权平均：

```
score = Σ(wᵢ × coveredᵢ) / Σ(wᵢ),   coveredᵢ ∈ {0, 1}
```

- `coveredᵢ`：该点到第 i 类设施的路网距离是否 ≤ 判定阈值（1000 m），
  是记 1、否记 0；若区域内根本没有该类设施，该项为 0
- `wᵢ`：类别权重，赛题点名的三类为 1.5，其余为 1.0
- 得分区间 0~1，1 表示最便利

**为何不用距离线性衰减**（`1 − d / threshold`）：判定阈值本身就是 1000 m，
一个距离 900 m 的设施按定义已经可及；若按线性衰减计分它只得 0.1 分，
于是覆盖率 100% 的区域也会被算成接近 0 而整片发红，与"覆盖率高"这一事实自相矛盾
（莞城实测即因此整片发红）。故采用「可及即满分」口径，实现在
`services/blindspot.py` 的 `_accessibility_score()`。

由于只在等时圈范围内着色，**图形外轮廓就是真实等时圈边界**，
颜色则表达可达性——一张图同时满足「等时圈热力图」与「盲区识别」两项评分要求。

### 3.4 为什么不用凸包做轮廓

凸包是"包含所有点的最小凸多边形"，会**把可达范围的凹陷与缺口全部抹平**，
画出来又变成接近圆的形状——这与直接画圆没有本质区别，
恰恰丢掉了"真实路网 ≠ 直线距离"这一核心结论。

因此前端**按网格单元逐个绘制半透明正方形色块**：相邻格子无缝拼接成连续的面，
完整保留凹陷与缺口（那是河流、铁路阻断的证据）。
再遍历每个可达格子，凡是某个方向没有相邻可达格子就描出那条边，
拼成完整外轮廓，边界因此比纯色块锐利（见 `js/layers.js` 的 `drawBoundary`）。

后端**不再计算凸包**：原 `polygon` 字段因前端始终未使用，已被移除。

### 3.5 设施点位采用形状 + 颜色双重编码

仅用颜色区分类别对色觉障碍人群不友好。因此十个类别各赋予一种形状
（圆形 / 十字 / 三角 / 菱形 / 方形 / 五角星 / 六边形 / 竖矩形 / 五边形 / 倒三角），
与颜色共同构成双重编码——即使完全无法辨色，也能靠轮廓区分设施类型。

### 3.6 关键参数的实测依据

| 参数 | 取值 | 依据 |
|---|---|---|
| 网格间隔 | 150 m | 200 m 与 150 m 算出的可达面积仅差 1.4%（1.44 vs 1.42 km²），统计口径已收敛；150 m 用于提升热力图细腻度 |
| 网格半径 | 1200 m | 实测 15 分钟可走 1056 m 路网距离，绕行系数 1.33~1.58 对应直线半径 670~790 m；1200 m 覆盖最坏情况并留余量，比初设 1500 m 省约 36% 无效调用 |
| 时间阈值 | 900 秒 | 15 分钟 |

## 四、多源 POI 数据清洗策略

### 4.1 问题：并集检索会被单一类别淹没

百度地点检索支持 `$` 分隔的多关键字并集检索（最多 10 个），
理论上一次请求即可拿到全部类别。但实测发现严重问题：

**在莞城老城区，1000 m 内各类设施共 104 个，返回的前 20 条里 18 条都是药店**，
菜市场、小学等类别被完全挤掉。

原因：接口只返回前 20 条，且按综合相关性排序而非按类别均衡。
据此统计会得出「该区域没有小学」这类严重失真的结论。

### 4.2 解决方案：按类别分别检索

改为每个类别单独发起请求：

```
菜市场 → 1 次请求 → 该类的全部结果
药店   → 1 次请求 → 该类的全部结果
...
```

代价：单次分析从 1 次检索变为 10 次。通过结果缓存与"按需指定类别"缓解。

### 4.3 归一化与清洗

| 步骤 | 处理 |
|---|---|
| 类别归一化 | 按 `FACILITY_CATEGORIES` 关键词表把 POI 归入 10 类民生设施 |
| 匹配优先级 | 顺序敏感，「小学」排在「药店」之前，避免"XX小学门口药店"被误判 |
| 半径裁剪 | 剔除超出检索半径的结果，保证统计口径一致 |
| 距离计算 | 用 Haversine 计算到中心点的球面直线距离 |
| 排序 | 按距离升序，便于后续取最近设施 |
| 去重 | 逐类检索天然避免跨类别重复计数 |

### 4.4 十类民生设施

菜市场、药店、小学、幼儿园、医疗、购物、公园、银行、养老、餐饮

其中**菜市场、药店、小学**为赛题明确点名的盲区判定类别，权重更高。

## 五、服务盲区识别算法

### 5.1 判定语义

对**15 分钟等时圈内的每个可达点**，判断其周边 1000 m 内能否找到指定类别的设施。
找不到 → 该点在该类别上属于盲区；**判定类别中缺失任一** → 该点记为服务盲区。

只判定可达点（而非全部网格点），因为走不到的地方本就不属于生活圈。

**判定类别 ≠ 统计类别**：检索与覆盖率统计默认覆盖全部 10 类，
但「是否盲区」默认只针对赛题点名的三类（菜市场 / 药店 / 小学，
见 `constants.BLINDSPOT_CATEGORIES`）。若改用全部 10 类判定，
养老这类普遍稀缺的设施会让几乎所有点都命中缺失，盲区率被推向 100%，失去区分度。
接口可通过 `blindspot_categories` 参数覆盖默认判定类别。

### 5.2 核心优化：直线初筛

对每个点、每个类别，记 `d` = 到该类最近设施的**直线距离**：

| 条件 | 结论 | 是否需要调 API |
|---|---|---|
| 该类在检索范围内无设施 | 必然盲区 | ❌ 否 |
| `d > 1000 m` | 必然盲区（路网距离 ≥ 直线距离） | ❌ 否 |
| `d < 625 m`（1000 ÷ 绕行系数 1.6） | 必然非盲区（路网 ≤ d × 1.6 < 1000） | ❌ 否 |
| `625 m ≤ d ≤ 1000 m`（灰色地带） | 需真实路网距离才能定论 | ✅ **是** |

前三类结论由几何性质保证成立，无需调用 API。

**实测效果**：

| 点位 | 判定总次数 | 实际调用算路 | 节省 |
|---|---|---|---|
| 松山湖 | 63 × 10 = 630 | 135（21.4%） | 78.6% |
| 莞城 | 55 × 10 = 550 | 103（18.7%） | 81.3% |

约**八成判定由初筛直接得出**。

### 5.3 灰色地带精算

对落入灰色地带的点，取直线距离最近的 **3 个候选设施**（而非 1 个，
因为"直线最近"未必是"路网最近"），调用批量算路取真实路网距离，
再按 `min(路网距离) ≤ 1000 m` 判定。

### 5.4 绕行系数的取值

`DETOUR_FACTOR` 取 **1.6**，依据是实测绕行系数 1.33~1.58。

取值偏小的后果：把真实盲区误判为"可达"（**漏报**）。
漏报比多算几个点严重得多，因此宁可保守。

### 5.5 POI 检索半径必须大于等时圈半径

盲区判定的是"每个点周边 1000 m"，而最远可达点距中心可达约 764 m，
它 1000 m 内的设施可能位于距中心 **1764 m** 处。

若 POI 只按 1000 m 半径检索，边缘点会因"远处明明有设施却没检索到"
而被误判为盲区。因此检索半径设为 **2000 m**。

## 六、降级容错设计

| 场景 | 降级策略 |
|---|---|
| 批量算路不可用（配额耗尽 / AK 失效） | 退化为「直线距离 × 绕行系数 ÷ 步行速度」估算，响应标记 `degraded: true` |
| 单个网格点算路失败 | 该点 `duration` 记为 `null`，视为不可达 |
| 个别类别检索失败 | 记入 `failed_categories`，前端显著提示，**不进入缓存** |
| 灰色地带精算失败 | 退回直线判定，标记不精确 |
| 逆地理编码失败 | 地址留空，不影响报告主体 |

**关键细节**：百度对算路失败的点返回 `duration = 0`。
若直接采信，这些点会被当成"0 秒到达"，在热力图上变成最核心区域。
必须识别为失败：`duration <= 0 → None`。

## 七、配额与性能优化汇总

| 手段 | 效果 |
|---|---|
| 直线初筛 | 砍掉约 80% 的盲区算路调用 |
| 网格半径实测修正（1500→1200 m） | 省约 36% 无效算路 |
| 批量算路分批（每批 50 终点） | 请求数从 10 降到 4 |
| 三级结果缓存（等时圈 / POI / 分析报告） | 重复查询零消耗，坐标量化到 50 m |
| 按需指定类别 | 调试时可从 10 类降到 3 类 |
| 并发限流 3 | 避免触发限流导致整批失败 |

单次完整分析：约 **网格点数（默认 197）+ 灰色地带精算次数 × 候选数（≤3）
+ 10 次地点检索**，两个样例点位实测约 600 条算路；
在批量算路日配额（5000 条）下可运行约 8 次（配合缓存实际更多）。

> 注：`/api/isochrone` 与 `/api/report` 的网格间隔均取配置
> `GRID_STEP_M`（默认 150 → 197 点），请求中 `step_m` 留空即可。

## 八、工程结构

```
backend/app/
├── core/       config(配置) constants(设施分类) samples(示例点位)
├── schemas/    models(请求/响应模型)
├── services/   baidu_client(限流重试) routematrix(批量算路) geocoding poi
│               isochrone(等时圈) blindspot(盲区) report(报告聚合)
├── routers/    health config poi geocode isochrone report
└── utils/      geo(距离/网格/坐标量化) cache(TTL+LRU)
```

分层原则：路由只做参数校验与响应组装，业务逻辑全部下沉到 services，
百度 API 的所有网络细节收敛在 `baidu_client` 一处。
